## Context

参见 `proposal.md` 的 Why。当前结果分配以 `sourceNodeId + outputId + itemIndex` 为查找键，而单项输出在每次 ComfyUI 执行中都会返回 `itemIndex = 0`，因此重复运行会命中并更新同一节点。结果状态更新也会遍历该工作流的全部受管结果，直接增加节点仍会让历史节点在新任务运行、失败或取消时被改写。

画布的具名输出端口已经允许多条连线，结果元数据也已经保存 `comfyuiPromptId` 和本地文件路径。本设计复用这些现有能力，把变更限制在 ComfyUI 本地集成内部。

## Goals / Non-Goals

**Goals:**

- 以 ComfyUI `prompt_id` 作为每次运行的稳定身份，为每次运行隔离结果节点。
- 深化结果节点分配 Module，使认领空节点、追加节点、连接、布局和历史识别集中在一个 Interface 后面。
- 保持已有画布中的成功结果和本地文件引用不变。
- 让执行测试可以从公开运行入口验证三次运行的完整画布结果。

**Non-Goals:**

- 不支持同一工作流节点并发运行或快速点击排队。
- 不新增独立的运行历史面板、分页、清理按钮或数量上限。
- 不改变 ComfyUI 输出文件命名、缓存目录或原生下载协议。
- 不修改通用画布端口、连线协议和其他生成节点的结果策略。
- 不改变用户更换工作流或调整暴露输出时现有的受管结果清理行为。

## Decisions

### 1. 在结果分配 Module 建立运行级 seam

`result-nodes.ts` 继续拥有结果节点图结构，并将现有分配 Interface 深化为接受运行上下文的形式：

```ts
ensureComfyResultNodeOps(
  source,
  definition,
  nodes,
  connections,
  { promptId, itemIndexes },
): CanvasAgentOp[]
```

调用者只提供本次 `promptId` 和实际输出索引；Implementation 负责寻找本次节点、认领空节点、追加节点、创建连线和计算位置。测试与执行调用者共用这一 seam。

选择该方案而不是在 `execution.ts` 内直接拼装节点，是因为节点身份、连接和布局属于同一组变化知识。删除该 Module 会迫使这些规则散落回工作流创建、执行完成和工作流重选等多个调用者，说明该 Module 能提供足够 Depth、Leverage 和 Locality。

备选方案是直接给 `itemIndex` 增加历史偏移量。该方案把 Comfy 单次输出序号和 TDCanvas 运行历史序号混为一体，批量输出时容易错位，因此不采用。

### 2. 复用 `comfyuiPromptId` 作为运行身份

完成结果已经在节点元数据保存 `comfyuiPromptId`。取得 `prompt_id` 后，结果分配 Module 立即将它写入本次待填充节点；完成结果继续沿用相同字段，不新增第二套运行 ID。

分配规则如下：

1. 优先查找 `sourceNodeId + outputId + itemIndex + comfyuiPromptId` 完全匹配的节点。
2. 本次运行尚无节点时，可以认领相同输出下无内容且没有 `comfyuiPromptId` 的预建空节点。
3. 含内容、含本地路径或含既有 `comfyuiPromptId` 的节点均视为历史结果，不可认领。
4. 无可认领节点时创建新的原生结果节点和从对应输出端口出发的新连线。

备选方案是在 `ComfyResultBinding` 中新增另一份 `runId`。由于 `prompt_id` 已持久化且天然唯一，再增加字段会产生两个必须保持一致的身份来源，因此不采用。

### 3. 提交成功后再分配本次结果节点

执行流程调整为：

```text
准备输入 --> 提交工作流 --> 获得 promptId
                           |
                           v
                  分配并标记本次结果节点
                           |
                           v
                  等待结果 --> 填充本次节点
```

提交前只更新工作流源节点的准备状态，不修改任何历史结果。取得 `promptId` 后，为每个预期输出建立本次占位节点；完成时按实际 `itemIndex` 补充分批结果。

如果提交前失败，不创建新的结果节点。如果提交后失败或取消，只更新匹配当前 `promptId` 的节点。缺失输出检查也只扫描当前运行，避免把历史批次错误标记为缺失。

备选方案是在点击瞬间生成客户端临时 ID。该方案需要在提交成功后再次将临时 ID 映射到 `prompt_id`，增加状态转换和恢复复杂度，因此不采用。

### 4. 新节点追加到受管结果列底部

结果分配 Module 读取同一源工作流的受管结果节点几何信息，以既有节点的最大底边为基准追加下一个节点，并保留当前输出侧水平间距。一次运行包含多个输出或批量条目时，按定义顺序和 `itemIndex` 顺序依次追加。

该规则避免依赖 `outputIndex + itemIndex`，因为不同输出和批量条目可能得到相同数值并发生重叠。用户手动移动历史节点时，新节点仍追加在当前受管结果集合的最下方。

### 5. TDD 只覆盖两个已确认 seam

- `runComfyWorkflowNode(ctx)`：以三个不同 `promptId` 模拟三次串行运行，断言三节点、三连线、三个独立媒体路径，并断言早期结果在后续成功、失败和取消后不变。
- `ensureComfyResultNodeOps(...)`：验证空节点认领、历史节点拒绝复用、运行级查找、批量补建和无重叠布局。

不对私有查找或布局函数直接编写测试；这些 Implementation 可在不改变 Interface 行为的情况下重构。

## Risks / Trade-offs

- [长时间重复运行会增加画布节点数量] → 本次遵循用户要求完整保留结果，不引入自动清理；用户仍可手动删除不需要的节点。
- [提交成功但等待结果失败会留下失败占位节点] → 仅该 `promptId` 的节点显示失败，保留可追溯性且不污染历史成功结果。
- [旧画布可能存在没有 `comfyuiPromptId` 的非空结果] → 非空内容或本地路径同样视为历史结果，避免被认领覆盖。
- [用户移动某个历史节点后可能拉长追加布局] → 以实际最大底边追加，优先保证不重叠；本次不实现自动整理。
- [回滚旧版本后旧逻辑可能再次复用多个历史节点中的第一个] → 回滚仅恢复程序文件，不应在旧版本中继续运行该工作流；画布数据和媒体文件本身不会因本变更迁移或删除。

## Migration Plan

1. 不执行批量数据迁移；运行时根据现有内容、本地路径和 `comfyuiPromptId` 判断历史节点。
2. 先通过结果分配 Interface 的测试，再调整执行流程，确保每个垂直切片保持可验证。
3. 更新产品文档中“重复运行复用原结果节点”的旧描述，并把本功能加入待验收记录和 `CHANGELOG.md` 的 `Unreleased`。
4. 完整测试、类型检查和正式构建通过后，在独立的真实 AITudou 画布中串行运行三次并检查三条连线、三个视频及历史稳定性。
5. 如需回滚，恢复变更前程序版本；不删除已生成节点或媒体文件。
